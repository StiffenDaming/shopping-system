### 4.2 关键设计判断：叶子深度不统一

这份分类里，**「其他乐器」「其他棋类」有三级，「围棋」的三级是具体商品类型**，而订单里的商品可能挂在**二级**（如"古筝"直接卖）或**三级**（如"入门普及筝"）。

因此：

- 数据模型**必须**用 `parent_id + level + path`，不能假设"只有两层"
- **商品只能绑定叶子节点**（叶子 = 没有子分类的节点，可能在 2 层或 3 层）
- 前端筛选：选一级 → 匹配其**所有后代**商品（`path LIKE '1/%'`）
- 面包屑与后台列表：显示全路径"琴 / 古琴 / 入门练习琴"

### 4.3 表结构建议

```sql
ALTER TABLE category
  ADD COLUMN parent_id BIGINT NOT NULL DEFAULT 0 COMMENT '父分类ID，0为一级',
  ADD COLUMN level INT NOT NULL DEFAULT 1 COMMENT '层级: 1/2/3',
  ADD COLUMN path VARCHAR(200) NOT NULL DEFAULT '' COMMENT '路径: 1/5/12',
  ADD COLUMN remark VARCHAR(200) DEFAULT NULL COMMENT '运营说明（后台可见，前台不展示）';
```

### 4.4 种子数据不要硬编码在 Java 里

72 个节点写进 `DataInitializer` 的 Java 数组会很难维护。建议：

- 新建 `backend/src/main/resources/data/categories.json`（树形或扁平带 parentCode）
- `DataInitializer` 读取 JSON，按顺序插入并回填 `parent_id` / `level` / `path`
- 好处：以后调分类只改 JSON，不碰 Java

## 五、变更三：模拟支付

### 5.1 定位说明（写论文时必须如实）

这是**模拟支付**：展示二维码 + 用户点击"我已完成支付"后由系统标记为已支付，**不校验真实到账**。
论文里不能写成"对接了支付宝/微信"，要写"模拟支付流程（二维码展示 + 手动确认），验证订单支付状态流转"。

### 5.2 表结构

```sql
ALTER TABLE orders
  ADD COLUMN pay_status INT NOT NULL DEFAULT 0 COMMENT '支付状态: 0-未支付, 1-已支付',
  ADD COLUMN pay_method VARCHAR(20) DEFAULT NULL COMMENT '支付方式: ALIPAY/WECHAT/UNIFIED',
  ADD COLUMN pay_time DATETIME DEFAULT NULL COMMENT '支付时间';
```

**订单状态保持不变**（PENDING/SHIPPED/COMPLETED/CANCELLED），支付状态是与其正交的第二个维度——这样对现有状态机、统计、推荐的影响最小。

### 5.3 规则

| 操作 | 规则 |
|---|---|
| 下单（checkout） | `status=PENDING`、`pay_status=0` |
| 支付（新增接口） | 仅本人订单；`status=PENDING` 且 `pay_status=0`；成功后写 `pay_status=1`、`pay_method`、`pay_time` |
| 发货（管理员） | **要求 `pay_status=1`**，否则提示"该订单未支付，不能发货" |
| 取消订单 | 仅 `status=PENDING` 且 `pay_status=0` 可自助取消；已支付需联系管理员（模拟退款） |
| 确认收货 / 强制完成 | 不变 |

### 5.4 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/orders/{id}/pay` | body `{payMethod:"ALIPAY"\|"WECHAT"\|"UNIFIED"}`，返回成功 |
| GET | `/api/orders/{id}`（已有） | 返回体新增 `payStatus/payMethod/payTime` |

二维码地址放 `application.yml`，便于替换：


## 六、方案对比（为什么不能用"固定二级"）

| | 固定二级 | 任意层级（本方案） |
|---|---|---|
| 能否表达"古筝→入门普及筝" | ❌ 只能两层 | ✅ |
| 能否允许"其他乐器→二胡"直接挂二级 | ❌ | ✅（叶子深度不统一） |
| 筛选逻辑 | 展开一层子类 | `path LIKE` 查后代 |
| 数据模型 | `parent_id` 够 | `parent_id + level + path` |
| 工作量 | 2.5 人日 | 3 人日（差 0.5） |
| 结论 | 不满足需求 | **采用** |

分类管理后台仍**不做**（72 个节点由 JSON 种子维护），省下最贵的一块；答辩可解释为"类目由平台预置，保证归类规范"。
