## 四、功能缺陷

### 4.1 库存扣减存在并发超卖（真实缺陷）

`OrderServiceImpl:99` 的写法是：

```java
product.setStock(product.getStock() - item.getQuantity());
productMapper.updateById(product);
```

这是**读—改—写**，两个并发请求会读到同一个库存值，各自减完再写回，导致超卖。

**修法**（条件更新，约 20 行）：

```sql
UPDATE product SET stock = stock - #{qty}
WHERE id = #{id} AND stock >= #{qty}
```

影响行数为 0 时抛 `库存不足`。这样由数据库保证原子性。

**风险**：改动订单核心链路，需要回归 `OrderApiTest`（13 个用例）。

### 4.2 上传目录未持久化

若保留 `/upload`，Docker 无 volume，重启丢图。
**若按第二节删除上传接口，此项自动消失。**

## 七、拟新增功能评估

### 7.1 图片验证码 + Redis

**环境现状**

- WSL 内 Redis 正在运行：`0.0.0.0:6379`，无密码，`redis-cli ping` 返回 `PONG` ✅
- 后端 `pom.xml` **没有** Redis 依赖 ❌
- 本地 `.m2` 仓库 **也没有** `lettuce` / `jedis` ❌

**这意味着**

1. 必须新增 `spring-boot-starter-data-redis`，**需要联网下载依赖**
   （本地 `mvn -o` 离线编译会直接失败；Docker 构建有阿里云镜像，之前构建成功过，应该没问题）
2. 后端容器访问 WSL 的 Redis 需要 `host.docker.internal`（Docker Desktop 通常提供），
   或给 compose 加 `extra_hosts: ["host.docker.internal:host-gateway"]`（尚未实测）
3. 验证码图片**不需要第三方库**：JDK 自带 `BufferedImage` + `Graphics2D` 就能画

**两种方案对比**

| 方案 | 优点 | 缺点 |
|---|---|---|
| Redis 存储 | 答辩可讲"用 Redis 做验证码缓存"；多实例共享 | 要下载依赖；要解决容器跨网络访问；多一个组件需要运维 |
| 进程内存储（ConcurrentHashMap + 过期） | 零依赖、零运维、改动最小 | 重启失效；多实例不共享（本项目单实例，够用） |

**需要你决定**。若答辩想强调 Redis，选第一种；若求稳，选第二种。

### 7.2 首页轮播图 + 热榜并列

**现状**

- 商品图是**正方形**（OSS 原图 1:1）
- 列表卡片用 `height: 200px` + `object-fit: contain`，不会拉伸 ✅
- 热榜现在是**横向条**（`.hot-strip`），在筛选栏下方

**方案**

- 首页顶部改为左右两栏：左侧轮播（容器 `aspect-ratio: 1`，图片 `object-fit: cover`），右侧热榜竖排
- 窄屏（< 900px）自动上下堆叠
- 纯前端改动，不涉及后端

**注意**：`object-fit: cover` 会裁掉边缘；若藏品图主体居中，可接受；若不想裁，用 `contain` + 背景色。
