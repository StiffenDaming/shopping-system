# 前端缓存与部署刷新笔记

> 收藏品商城系统 · 2026-11-17 整理
> 适用：Docker 部署（nginx）+ Vite 构建 + Vue3 SPA

---

## 0. 一句话结论

**"改了代码但页面不更新"，99% 是这两件事之一：**

1. **容器里还是旧镜像**（`docker compose up -d` 不会自动重建）
2. **浏览器还在用旧缓存**（旧 `index.html` 指向旧 JS，而旧 JS 被标了 `immutable`）

判断哪个：**先访问 `http://localhost/build-info.json`**。

---

## 1. 现象与根因

| 现象 | 根因 | 归类 |
|---|---|---|
| 清缓存后才显示新页面 | 旧 `index.html` 被启发式缓存，指向旧哈希 JS | 浏览器 |
| 清缓存后新开窗口又变旧 | 新窗口共用同一份磁盘缓存；或清缓存不彻底 / 旧标签页还在 | 浏览器 |
| 清了缓存还是旧页面 | 容器跑的是旧镜像 | Docker |
| 页面白屏 / 资源 404 | 旧入口指向已被删除的旧资源，且旧资源缓存已失效 | 浏览器 |
| `localhost` 新、`127.0.0.1` 旧 | 两者是**不同源**，缓存各自独立 | 浏览器 |

**完整链条**（本次真实故障）：

```
旧 nginx.conf
  ├─ index.html   → 没有任何 Cache-Control（走启发式缓存）
  └─ *.js / *.css → expires 30d + immutable（30 天内连校验都不发）
        ↓
重新构建镜像后，浏览器手里仍是旧 index.html + 旧 JS
        ↓
页面完整渲染出旧界面（不是白屏）→ 清缓存才断链
        ↓
新窗口复用同一磁盘缓存 → 又变旧
```

## 2. 缓存指令速查

### 2.1 强缓存（不发请求，直接用本地副本）

| 指令 | 含义 | 适用 |
|---|---|---|
| `max-age=31536000` | 一年内直接用本地副本 | 带哈希指纹的资源 |
| `immutable` | 连"用户按刷新"都不重新校验 | 带哈希指纹的资源 |
| `no-store` | **完全不缓存**，每次都要新文件 | `index.html`、接口响应 |
| `no-cache` | 缓存但每次必须回源校验 | 需要协商的 HTML |

> ⚠️ `no-cache` 不是"不缓存"，它是最容易被误解的指令。真正"不缓存"是 `no-store`。

### 2.2 协商缓存（发请求，由服务端判断是否 304）

| 响应头 | 请求头 | 行为 |
|---|---|---|
| `ETag` | `If-None-Match` | 内容指纹比对，一致返回 304 |
| `Last-Modified` | `If-Modified-Since` | 时间比对，一致返回 304 |

**关键坑**：只给 `ETag` / `Last-Modified`、不给 `Cache-Control` 时，浏览器会走**启发式缓存**
（按 `(当前时间 - Last-Modified) × 10%` 估算有效期），完全不受你控制。旧 `index.html` 就是掉进这个坑。

### 2.3 nginx 指令的副作用

`expires` 指令会**自己加一条** `Cache-Control`，和 `add_header` 叠加会出现重复响应头：

```nginx
expires 30d;                                    # → Cache-Control: max-age=2592000
add_header Cache-Control "public, immutable";   # → Cache-Control: public, immutable
# 结果：两条 Cache-Control
```

正确写法：**用 `expires off` 关掉自动行为，只用 `add_header`**。

## 3. 本项目的缓存策略

`frontend/nginx.conf` 三段规则，各管一件事：

```nginx
# ① 入口 HTML：永不缓存
location = /index.html {
    expires off;
    add_header Cache-Control "no-store, no-cache, must-revalidate" always;
    add_header Pragma "no-cache" always;
    try_files $uri =404;
}

# ② SPA 路由回退（history 模式）
location / {
    try_files $uri $uri/ /index.html;   # 内部跳转后仍命中 ① 的规则
}

# ③ 带哈希指纹的静态资源：一年强缓存
location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff|woff2|ttf|eot)$ {
    expires off;
    add_header Cache-Control "public, max-age=31536000, immutable" always;
}
```

**为什么这样配是安全的**：

Vite 构建时按**文件内容**生成哈希文件名（`index-C1LIbS6W.js`）。
代码一改，文件名必然变化 → 浏览器请求的是一个**从未缓存过的新 URL** → 天然失效。
所以静态资源可以放心设一年 `immutable`，性能最好；
而入口 `index.html` 必须 `no-store`，它是"指针"，永远要拿最新的一版。

**这是 SPA 部署的标准组合**：`index.html` 不缓存 + 资源文件永久缓存。

### 3.1 实测响应头（本次验证）

```
GET /                → Cache-Control: no-store, no-cache, must-revalidate
GET /products        → Cache-Control: no-store, no-cache, must-revalidate   ← SPA 路由同样生效
GET /assets/*.js     → Cache-Control: public, max-age=31536000, immutable
GET /build-info.json → Cache-Control: no-store   + 构建时间戳
```

```
│   ├─ 时间戳是旧的或 404

│         │
│         └─ 纯浏览器缓存的处理：
│             Ctrl + Shift + R（硬刷新）一次即可，之后 no-store 永久生效
```

## 6. 浏览器操作为什么有时"不管用"

| 操作 | 实际行为 | 能否绕过旧缓存 |
|---|---|---|
| `F5` / `Ctrl+R` | 普通刷新：主文档回源，但 `immutable` 子资源**不校验** | ❌ 常常不够 |
| `Ctrl+Shift+R` | 硬刷新：绕过缓存重新下载文档和子资源 | ✅ 推荐 |
| 清除浏览数据 | 清磁盘缓存；但**已打开的标签页内存里还有旧副本** | ⚠️ 需关掉旧标签 |
| 新开窗口 | 与旧窗口**共用同一磁盘缓存**，不是新环境 | ❌ 无效 |
| 无痕窗口 | 独立临时缓存，能看到新页面，但关掉即失效 | ⚠️ 只能验证，不算修复 |
| `localhost` ↔ `127.0.0.1` | 两个**不同源**，缓存互不相干 | ⚠️ 容易自己骗自己 |

> 所以"清缓存有效、新开窗口失效"完全正常——它证明的是**浏览器缓存问题**，不是服务端问题。

## 7. 其他容易踩的坑

### 7.1 Docker 构建缓存

`COPY . .` 之后是 `RUN npm run build`。只要源码变了，这一层就会重建。
但如果**只改了 `nginx.conf`**——它也是通过 `COPY . .` 进去的，同样会触发重建，没问题。

真正要注意的是：`docker compose up -d` **不构建**，只有 `--build` 或 `docker compose build` 才构建。

### 7.2 `.dockerignore` 必须排除 `node_modules`

否则会把宿主机（Linux 版）的 `node_modules` 打进构建上下文，而且其中的符号链接
（`node_modules/.bin/esbuild`）会让 Docker 在 WSL 路径上直接报错：

```
ERROR: invalid file request node_modules/.bin/esbuild
```

`frontend/.dockerignore`：
```
node_modules
dist
.idea
.vscode
*.log
```

### 7.3 镜像里的 `npm ci` 与宿主机依赖无关

容器内是独立安装（`npm ci` + 国内镜像），宿主机 `node_modules` 只影响本地开发，不进镜像。

### 7.4 后端也遵循同样的道理

Java 是编译型，改代码不重建镜像，容器里就还是旧 jar。判断方法同理：
```bash
curl http://localhost:8081/api/...   # 看新接口在不在
```

## 8. 命令速查卡

```bash
# 构建并启动（带 Key）

# 只看容器状态
docker ps --format "{{.Names}}\t{{.Status}}\t{{.Ports}}"

# 构建时间戳（判断镜像新旧）
curl -s http://localhost/build-info.json

# 验证缓存头
curl -sI http://localhost/ | grep -i cache-control
curl -sI http://localhost/assets/xxx.js | grep -i cache-control

# 验证新代码进了镜像
docker exec shopping-frontend sh -c "grep -rl '关键词' /usr/share/nginx/html/assets"

# 看容器日志
docker logs --tail 50 shopping-frontend
docker logs --tail 50 shopping-backend

# 强制干净重建（极少数情况，重装依赖层）
docker compose build --no-cache frontend && docker compose up -d frontend
```
