### 分类相关的现状（改造重点）

`category` 表是**扁平表**，没有层级概念：

```sql
CREATE TABLE `category` (
  `id` BIGINT AUTO_INCREMENT,
  `name` VARCHAR(50) NOT NULL,
  `sort` INT NOT NULL DEFAULT 0,
  `create_time` DATETIME,
  PRIMARY KEY (`id`)
)
```

- 种子数据 7 条：文玩雅器、古玩雕像、书刊影集、钱币票证、潮玩盲盒、动漫游戏周边、镇馆之宝
- `product.category_id` 为单值外键
- 接口只有 `GET /api/categories/list`（**没有增删改**——第一轮改造时因"无前端入口"主动删掉了）
- **分类被 17 个后端文件、3 个前端文件引用**
- 推荐模块把分类写进画像向量：`CAT:{categoryId}`（见 `ProfileService`、`RecommendService`、`ProfileQueryService`、`CatalogCache`）

## 三、方案对比

### 方案 A：二级分类（固定两层）

| 层 | 改动 |
|---|---|
| 数据库 | `category` 加 `parent_id BIGINT DEFAULT 0`（0 表示一级） |
| 后端 | `Category` 实体 +1 字段；`CategoryService` 增加 `listTree()`；`ProductServiceImpl` 查询时把一级分类展开为其子分类 ID；商品保存校验只能选叶子 |
| 前端 | `Products.vue` 两级联动筛选；`ProductManage.vue` 分类下拉→级联选择；`Dashboard.vue` 分类统计按一级汇总 |
| 数据 | 重灌分类 + 更新 `product.category_id` 到叶子 |
| 工作量 | **约 2.5 人日** |
| 风险 | 低。单纯加一列，不动其它表 |
| 局限 | 想做三级要再改一次：加 `level`、改筛选逻辑、改前端 |

### 方案 B：任意层级（N 级）

| 层 | 改动 |
|---|---|
| 数据库 | `parent_id` + `level` + `path`（如 `1/5/12`，支持 `LIKE '1/5/%'` 查后代） |
| 后端 | A 的全部；**新增分类树 CRUD**：新增/改名/移动/删除；循环校验（不能把父节点移到自己的子孙下）；删除约束（有子分类或有商品时禁止删）；全路径名（"书法 > 碑帖 > 拓本"）；后代查询 |
| 前端 | A 的全部；**新增「分类管理」页面**：树形表格 + 新增/编辑/删除/排序对话框 + 路由 + 菜单 |
| 推荐 | 画像的 `CAT:` 向量需按祖先汇总，推荐理由要能说出"书法类"这种上级名称 |
| 数据 | 重灌 + 迁移 `product.category_id` |
| 工作量 | **约 5~6 人日**（比 A 多出的主要是分类管理后台与各项校验） |
| 风险 | 中。删除/移动规则容易出边界 bug；分类管理后台是新页面，要补测试 |

### 方案 C：数据结构按三级、UI 支持三级、**不做分类管理后台**（推荐）

- 数据模型用 B 的（`parent_id` + `level` + `path`），一次到位
- 前端用 Element Plus 的 `el-cascader`，天然支持任意层级，**代码量与二级几乎一样**
- 分类仍由 `DataInitializer` 预置，用 SQL 维护——省掉最大的一块工作量（管理后台）
- 工作量：**约 3 人日**
- 答辩说法："分类体系由平台预置，保证商品归类规范；商家/用户不自行建类目"——这条在电商里成立（类目由平台运营维护）

> 如果老师一定会问"分类怎么维护"，再补一个极简分类管理页（树形表格 + 增删改），**+1 人日**，即方案 C+。
